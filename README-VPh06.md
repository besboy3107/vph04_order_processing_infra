# VPh06 — Кейс 3, часть 3: JWT-админка, метрики, ранжирование лидов

Третья (финальная) часть кейса. Поверх инфраструктуры (часть 1) и бэкенда+фронта
с авторизацией (часть 2) добавлено: JWT-авторизация, CRUD услуг в таблице, сбор и
визуализация поведенческих метрик, интеллектуальное ранжирование заявок и закрытие
контура до единственной точки входа.

## Что сделано в части 3

### 1. Авторизация админ-панели через JWT
- Новая таблица `admins` (логин + хеш пароля `pbkdf2_sha256`).
- Эндпоинты `/api/auth`: `check` (есть ли админ), `register` (только пока админов нет),
  `login` (выдаёт JWT), `me` (профиль по токену).
- Пока в системе нет ни одного админа — на странице входа видна кнопка
  «Зарегистрироваться». После регистрации первого админа кнопка пропадает.
- Токен (HS256) хранится в `sessionStorage`, шлётся заголовком `Authorization: Bearer`.
- Реализация на стандартной библиотеке Python (hmac/hashlib/base64) — **без новых
  зависимостей**: requirements.txt не разрастается, образ собирается быстро.

### 2. Управление услугами (CRUD в таблице)
- В админ-панели услуги добавляются, **редактируются прямо в строке** (кнопка «Изм.»
  → поля ввода → «Сохр./Отмена») и удаляются. Всё через `/api/admin-settings`
  (`GET/POST/PUT/DELETE`). Изменения сразу видны в выпадающем списке на сайте.

### 3. Поведенческие метрики + heatmap
- Клиентский сайт раз в секунду шлёт `POST /api/behavior-metrics`:
  `time_on_page`, `buttons_clicked`, `cursor_positions`, `return_frequency`.
- Метрики **анонимные и append-only** — никакой привязки к заявке и проверок
  `application_id` (как требует урок: «просто собирать анонимные метрики»).
- Кнопка «📊 Статистика пользователей» в админке открывает модалку:
  - среднее и максимальное время на странице за **день / неделю / месяц**
    (`GET /api/behavior-metrics/stats`);
  - **heatmap** наведения курсора на canvas — плотность позиций курсора
    (синий → красный), построена из нормированных координат (0..1), поэтому
    не зависит от разрешения экрана клиента.

### 4. Ранжирование заявок по «температуре» лида
- `backend/app/core/scoring.py` — чистая функция оценки (легко тестируется):
  балл 0..100 из бюджета, размера компании, роли заполняющего, срочности и объёма.
- `GET /api/applications` возвращает заявки с полем `lead` (`score`, `temperature`
  hot/warm/cold, `department`, `needs_manager`, `reasons`) и **сортирует по убыванию
  приоритета** — горячие вверху.
- В админке: бейдж температуры + балл, рекомендованный отдел, кнопка «Просмотр» →
  модалка со всеми деталями заявки и способом связи.
- `db/seed_test_applications.sql` — 10 тестовых заявок (4 горячих / 3 средних /
  3 холодных) с **разными** критериями срочности.

### 5. Безопасность: одна точка входа
- `pgadmin` и `registry` вынесены в compose-профиль `tools` и **по умолчанию не
  поднимаются**. Рабочий `docker compose up -d` стартует только
  `postgres`, `backend`, `nginx`, `watchtower`.
- Backend и PostgreSQL наружу не публикуются (`expose`), nginx слушает только
  `127.0.0.1:8080` и проксируется системным Nginx по HTTPS (443). Прямое обращение
  к портам backend/БД снаружи невозможно.
- nginx устойчив к выключенному pgAdmin: апстрим резолвится по запросу через
  docker-DNS (`resolver 127.0.0.11`), поэтому контейнер не падает на старте.

Для обслуживания (снять скриншоты pgAdmin, проверить реестр) инструменты
поднимаются явно:

```bash
docker compose --env-file .env --profile tools up -d pgadmin registry
```

## Проверка (локально, через nginx :8080)

| Проверка | Ожидание | Факт |
|----------|----------|------|
| `GET /api/health` | 200 | `{"status":"ok"}` |
| `GET /api/docs` | 404 (Swagger закрыт) | 404 |
| `GET /api/auth/check` (до регистрации) | `has_admin:false` | ✅ |
| `POST /api/auth/register` | 201 + token | ✅ |
| `GET /api/auth/check` (после) | `has_admin:true` | ✅ |
| `POST /api/auth/register` ещё раз | 403 | ✅ |
| `GET /api/applications` без токена / с битым | 401 | ✅ |
| `POST /api/admin-settings` с токеном | 201 | ✅ |
| `GET /api/applications` (после сида) | 4 hot / 3 warm / 3 cold, сортировка | ✅ (90,80,74,64 / 42,41,40 / 24,18,10) |
| `POST /api/behavior-metrics` (публичный) | 201 | ✅ |
| `GET /api/behavior-metrics/stats` | агрегаты | ✅ |

Применение тестовых заявок:

```bash
docker compose --env-file .env exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" < db/seed_test_applications.sql
```

## Миграция с части 2
Схема `behavior_metrics` сменилась (анонимная вместо 1:1 к заявке). При старте
backend сам дропает старую таблицу (если в ней осталась колонка `application_id`)
и пересоздаёт новую — ручных действий не требуется. Таблица `applications` не трогается.

## Инструмент
Урок рассчитан на Cursor; проект выполнен через **Claude Code** (CLI-агент от Anthropic
в терминале) — функционально эквивалентный агент. Деплой на VPS, конфиги и сборка
выполнялись через Claude Code по SSH. Подробнее о проверках — в [`docs/verification.md`](docs/verification.md).
